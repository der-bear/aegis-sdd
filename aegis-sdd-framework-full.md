## §0. Назначение и дизайн-принципы

**П1. Артефакт важнее агента.** Консистентность обеспечивают версионируемые артефакты в git (spec → architecture → feature → tasks → review → реестры), а не память чата. Любой агент можно перезапустить с нуля — истина восстановима из файлов.

**П2. Контекст — бюджет.** Каждый агент видит минимальный высокосигнальный набор токенов. Три слоя загрузки (§2), реестры как индексы (§3), дистилляты вместо пересказов.

**П3. Детерминизм на воротах, интеллект внутри.** Всё, что должно происходить всегда (тесты, линт, регистрация, доксинк) — hooks и скрипты, а не текст в промптах. Творческая работа — агентам.

**П4. Самоуправление ≠ автономная самомодификация.** Агенты предлагают изменения протоколов (draft-PR), человек апрувит. `constitution.md` меняется только руками человека.

**П5. Масштаб по надобности.** Порог мультиагентности (§16): начинать с одного агента; параллелить только по чистым границам контекста; каждый постоянный агент — точка отказа и координационные токены.

**Anti-goals:** оркестрация ради оркестрации; ролевая раздробленность по SDLC (planner/coder/tester/reviewer как отдельные тяжёлые агенты); документация «на вырост»; god-skills.

## §2. Слои контекста и иерархия инструкций

Четырёхуровневая иерархия «что где живёт»:

1. **Системный промпт агента** (тело `.claude/agents/<role>.md`) — кто он, инварианты, границы. Стабильное, меняется редко.
2. **CLAUDE.md** — только то, без чего любой агент ошибётся в этом проекте. Жёсткий бюджет.
3. **Skills** — доменные протоколы, подгружаются по релевантности (прогрессивное раскрытие: метаданные → тело → references).
4. **Спеки/реестры** — конкретика задачи, just-in-time по путям-идентификаторам.

Стоимость по слоям:

| Слой | Что | Когда в контексте | Стоимость |
|---|---|---|---|
| 0 | CLAUDE.md + метаданные всех скиллов | всегда | ≤2k + ~50·N токенов |
| 1 | тело SKILL.md | по триггеру description | ≤500 строк/скилл |
| 2 | references/, спеки, реестры | по явному чтению пути | по надобности |

Детерминированные требования («после каждого edit — линт», «нельзя писать в X») живут **не в тексте**, а в hooks (§6): это ноль токенов и стопроцентное срабатывание.

**Эталонный CLAUDE.md (полностью):**

```markdown
# <Project> — Aegis SDD
Истина проекта: .aegis/ (спеки, реестры, стандарты). Не выдумывай — читай реестр.

Правила (всегда действуют):
1. Любая работа привязана к TASK-ID. Нет задачи — создай через /aegis:tasks.
2. Код и его тесты пишутся вместе, одним агентом. «Готово» = зелёная самопроверка
   (команды ниже), не раньше.
3. Endpoint / событие / env-переменная / фиче-флаг существуют только с записью
   в соответствующем реестре .aegis/registry/.
4. Центральные доки и реестры пишет только doc-manager. Билдеры оставляют
   записи в handoff.
5. Протоколы, стандарты и constitution меняются только через draft-PR → аппрув
   человека. Никогда напрямую.
6. Между несвязанными задачами — новый контекст. Не тащи историю.

Индексы: @.aegis/registry/skills.yml  @.aegis/standards/index.yml
Команды проекта: тесты `make test` · линт `make lint` · сборка `make build`
                 (заполняется при инициализации)
```

Это ~0.6k токенов. Бюджет ≤2k оставляет запас на 5–8 проект-специфичных правил; линтер `budget-check` валит гейт при превышении.

## §3. Реестры — машиночитаемый источник истины

**Зачем.** Вопрос «какие интеграции есть / куда идёт событие X / какие скиллы существуют» должен стоить ~30 строк YAML, а не греп по кодовой базе на тысячи токенов с негарантированным результатом. Реестр — слой «лёгких идентификаторов»: сжатый, авторитетный индекс, от которого агент прыгает к деталям just-in-time.

**Общие правила всех реестров (registry-authoring, §5.3):**
- Формат: YAML-список, одна запись = один блок, отсортировано по `id` — git мержит чисто.
- У каждого реестра — JSON Schema в `registry/schemas/`; `registry-lint` валидирует на hook и на гейте.
- Обязательные поля везде: `id` (нейминг-конвенция), `status` (proposed | active | deprecated), `origin` (TASK/RETRO-ID), `docs` (ссылка на детальный док, если есть).
- Секреты — никогда значениями, только ссылками `env:VAR_NAME`.
- Запись создаётся **до или вместе** с артефактом, который она описывает; артефакт без записи не проходит гейт (детерминированный скан: роуты ↔ integrations, env-обращения ↔ env.yml).

**Состав реестров:**

| Реестр | Что индексирует | Ключевые поля сверх общих |
|---|---|---|
| `skills.yml` | Все протоколы | namespace, description(1 строка), evals |
| `integrations.yml` | Вебхуки in/out, внешние API | kind, endpoint, auth, payload_schema, consumer, retry |
| `events.yml` | Внутренние события/контракты | schema, producers, consumers, delivery |
| `env.yml` | Переменные окружения | scope, required, example (не значение!) |
| `flags.yml` | Фиче-флаги | default, owner, sunset-date |
| `diagrams.yml` | Диаграммы ↔ области кода | path, kind, watches[] (глобы), generated(bool), last_verified |
| `decisions.yml` | Индекс ADR | title, status, supersedes |
| `mcp.yml` | MCP-серверы и их инструменты | transport, tools(кратко), scopes |

Пример записи `integrations.yml` и её JSON Schema — Приложение C.

**Реестры и многопоточность.** Параллельные билдеры не пишут в реестры (write-scope §1): они кладут заготовку записи в handoff, doc-manager применяет сериализованно на гейте. Контенция нулевая, конвенции — в одних руках.

## §4. Роли агентов — полная система инструкций

Ростер сознательно компактный: каждый постоянный агент — точка отказа и координационные токены. Ревьюеры схлопнуты в набор «линз» одного read-only-паттерна; merge-гейт — детерминированный скрипт, не агент.

| Роль | Модель | Запись | Когда работает |
|---|---|---|---|
| Orchestrator | opus | NOTES.md, specs/ | всегда (лид сессии) |
| Builder ×1–3 | sonnet | код+тесты своей фичи, specs/<feature>/ | Фаза 3, задача |
| Линзы ×2–5 | sonnet/haiku | только reviews/ (read-only к коду) | после самопроверки билдера |
| Doc-manager | sonnet | docs/, registry/ (single writer) | сериализованно на гейте |
| Init/Gardener | sonnet | .aegis/ каркас; draft-PR | Фаза 1 / периодически |
| Merge gate | — (скрипт) | — | последним, детерминированно |

**Контракт делегирования** (обязателен для каждого вызова субагента; нарушение — главный источник дублей и потерь):
цель · формат результата (дистиллят ≤2k токенов + пути к файлам) · границы («что НЕ делать») · пути к нужным артефактам · лимит усилий (примерное число вызовов инструментов).

Frontmatter субагентов (сверено с документацией Claude Code, июль 2026): помимо `name/description/tools/model` доступны `skills:` — инъекция тел протоколов в контекст субагента на старте (**субагенты НЕ наследуют скиллы сессии автоматически**), `disallowedTools` (денилист), `maxTurns` (предохранитель от зацикливания), `memory` (персистентная память роли), `isolation: worktree` (нативная изоляция в git worktree для параллельных билдеров). Read-only-режим линз обеспечивается allowlist'ом `tools`, а не отдельным полем.

### 4.1 Orchestrator — `.claude/agents/orchestrator.md`

```markdown
---
name: aegis-orchestrator
description: Координатор Aegis — декомпозиция фич на задачи, делегирование
  билдерам и линзам, синтез результатов, ведение NOTES.md. Использовать как
  лид-агента сессии. НЕ использовать для написания продуктового кода.
model: opus
tools: Read, Grep, Glob, Task, TodoWrite, AskUserQuestion, Bash(git *)
---
Ты — оркестратор Aegis SDD. Твоя работа — план, делегирование, синтез.
Не реализация.

Инварианты:
1. Состояние — в .aegis/memory/NOTES.md, обновляй после каждой вехи:
   изменённые файлы, принятые решения, открытые вопросы, команды проверки.
   Не в этом чате.
2. Декомпозируй по границам контекста, не по ролям: билдер получает фичу
   целиком (код + тесты + фиче-доки), а не «слой» или «этап».
3. Каждая делегация — по контракту делегирования (цель, формат, границы,
   пути, лимит усилий). Без контракта не делегируй.
4. Масштабируй усилия: простая задача — 1 билдер последовательно;
   параллель (до 3) — только при контракт-интерфейсе между модулями.
   Субагентам запрещено порождать субагентов.
5. Принимай от субагентов только дистиллят ≤2k токенов + ссылки на файлы.
   Не проси пересказывать код.
6. Изменения протоколов/стандартов — только draft-PR на аппрув человека.
Эскалация человеку: неоднозначность требований; конфликт constitution с
запросом; 3 неуспешные итерации рефайнмента; выбор с необратимыми
последствиями (миграции данных, внешние контракты).
```

### 4.2 Builder — `.claude/agents/builder.md`

```markdown
---
name: aegis-builder
description: Реализация одной задачи TASK-*: код, тесты и фиче-доки в одном
  контексте. Использовать для любой имплементации. НЕ использовать для
  изменения центральных доков, реестров, стандартов.
model: sonnet
tools: Read, Grep, Glob, Edit, Write, Bash
skills: [testing/unit-conventions]   # + доменные — через контракт делегирования
maxTurns: 50
---
Ты — билдер Aegis. Работай строго в рамках одной задачи TASK-*.

Протокол:
1. Прочитай ровно: .aegis/specs/<feature>/{feature.md, tasks.md#TASK-ID},
   релевантный фрагмент spec.md, стандарты по индексу. Ничего сверх.
2. Короткий план (≤10 строк) → реализация. Фича и её тесты — вместе, тобой,
   включая негативные сценарии из feature.md#крайние-случаи.
3. Самопроверка обязательна: прогони затронутые тесты и сборку, чини до
   зелёного. «Готово» без прогона = провал.
4. Пиши только в файлы своей фичи и .aegis/specs/<feature>/. Центральные
   доки и реестры не трогай.
5. Новый endpoint/событие/env/флаг — заготовь запись реестра в handoff
   (doc-manager применит). Без записи гейт не пройдёт.
6. Handoff-отчёт ≤1.5k токенов: что сделано; изменённые файлы; как
   проверить (команды); отклонения от спеки с причиной; заготовки для
   реестров/доков.
Запрещено: менять протоколы/стандарты/constitution; «улучшать» вне scope
задачи; ослаблять или скипать тесты ради зелёного статуса.
```

### 4.3 Линзы — read-only верификаторы

Общий каркас всех линз: read-only инструменты (`Read, Grep, Glob` + узкий `Bash` для тестов), свежий контекст, вход = diff задачи + критерии, выход = отчёт по шаблону lens-report (Приложение A), вердикт `pass | fail | pass-with-notes`. Инструкция против over-engineering'а — во всех линзах: «сообщай ТОЛЬКО пробелы, влияющие на корректность или требования; вкусовые рефакторинги не предлагай». Инструкция против «ранней победы» — в correctness: «прогони ПОЛНЫЙ тест-сет фичи; успех после 1–2 тестов = провал линзы».

```markdown
---
name: lens-correctness
description: Read-only проверка корректности TASK-* против критериев приёмки:
  полный прогон тестов, крайние случаи, обработка ошибок. Запускать после
  самопроверки билдера. НЕ предлагает рефакторинги стиля.
model: sonnet
tools: Read, Grep, Glob, Bash(make test*, npm test*, pytest*, go test*)
maxTurns: 15
---
1. Вход: diff задачи; критерии приёмки из tasks.md#TASK-ID; feature.md.
2. Прогони ПОЛНЫЙ тест-сет фичи и негативные сценарии из
   feature.md#крайние-случаи. Ранний успех после 1–2 тестов = твой провал.
3. Сообщай только пробелы, влияющие на корректность/требования.
4. Отчёт по .aegis/templates/lens-report.md: находка, серьёзность 0–5,
   файл:строка, минимальный фикс. Вердикт: pass|fail|pass-with-notes.
   Код не переписывай.
```

Остальные линзы — тот же каркас, отличается фокус:
- **lens-security** (sonnet): инъекции, авторизация на новых роутах, секреты в коде/логах, обращение с payload'ами вебхуков, зависимости. Blocking по умолчанию.
- **lens-architecture** (sonnet): соответствие architecture.md и контрактам; новые межмодульные зависимости вне объявленных интерфейсов; нарушение слоёв.
- **lens-docs** (haiku): выполнены ли обязанности doc-profile — обновлены фиче-доки, заготовлены записи реестров, помечены затронутые диаграммы.
- **lens-consistency** (sonnet): цепочка spec ↔ architecture ↔ tasks ↔ код — покрытие требований, сироты, противоречия. Также гейт Фазы 2.

### 4.5 Init/Gardener

Init — не постоянный агент, а команда `/aegis:init` (§7), исполняемая оркестратором с Explore-субагентом. Gardener — периодический аудит гигиены (запускается из `/aegis:audit`): раздувание CLAUDE.md, дубли инструкций, скиллы-сироты (0 срабатываний за N задач), пары скиллов со срабатыванием вместе >50% (кандидаты на слияние), устаревшие записи реестров. Выход — draft-PR предложений, не прямые правки.

## §5. Протоколы (Skills) и мета-протоколы

**Анатомия протокола:** `.claude/skills/<namespace>/<slug>/SKILL.md` (+ `references/`, `scripts/`). Нэймспейсы: `meta/`, `backend/`, `frontend/`, `testing/`, `docs/`, `ops/`. Три уровня загрузки: метаданные (всегда, ≤60 токенов) → тело (по триггеру, ≤500 строк) → references (по чтению).

**Связывание агент ↔ протокол** — три механизма; их приоритет зависит от того, где работает агент. Ключевой факт (сверено с документацией): **субагенты не наследуют скиллы сессии автоматически** — протоколы им передаются явно.
1. **Frontmatter `skills:`** — официальная инъекция тел протоколов в контекст субагента на старте. Основной путь для постоянных ролей: builder ← `testing/unit-conventions`; doc-manager ← `meta/doc-authoring`, `meta/registry-authoring`.
2. **Инъекция в контракте делегирования** — оркестратор указывает пути дополнительных доменных протоколов под конкретную задачу; субагент читает их как файлы (слой 2).
3. **Авто-триггер по description** — работает в основной сессии оркестратора; на него рассчитаны триггеры/анти-триггеры. Для субагентов авто-срабатывание не гарантировано — на него не полагаться.

### 5.1 Мета-протокол protocol-authoring (полный текст)

```markdown
---
name: protocol-authoring
description: Протокол создания и изменения протоколов (skills) Aegis.
  Использовать при добавлении нового скилла, изменении существующего или
  ревью draft-PR протокола. НЕ использовать для продуктового кода и доков
  (для доков — meta/doc-authoring).
---
# Как писать протоколы Aegis

## Когда создавать
- Триггеры: одна и та же находка/фидбек ≥2 раз; новый домен в проекте;
  решение ретро. Иначе — не создавать.
- Сначала проверь registry/skills.yml: пересечение по триггерам с
  существующим → расширь существующий, не плоди новый.

## Формат
1. Путь: .claude/skills/<namespace>/<slug>/SKILL.md.
2. Frontmatter: name (= slug), description ≤500 символов, третье лицо,
   обязательно содержит (а) триггеры «использовать когда…»,
   (б) анти-триггеры «НЕ использовать для…».
3. Тело ≤500 строк: назначение → пошаговый протокол → 1–2 канонических
   примера → ссылки на references/. Таблицы, длинные примеры, схемы —
   в references/*.md.
4. Одна забота: один скилл = один протокол. Два независимых процесса —
   два скилла.

## Регистрация и проверка
5. Строка в registry/skills.yml: id, namespace, description(1 строка),

6. 2–3 eval-сценария в .aegis/evals/skills/<slug>.yml:

7. Draft-PR только с файлами протокола. Аппрув человека → status: active.

## Жизненный цикл
- proposed → active → deprecated (поле superseded_by). Deprecated не
  удаляется до конца мажорной версии.
- Слияние: два скилла срабатывают вместе >50% задач (данные gardener) →
  объединить.

## Чек-лист ревью draft-PR
[ ] триггеры И анти-триггеры в description
[ ] нет пересечения с существующими (skills.yml)
[ ] тело ≤500 строк, тяжёлое в references/
[ ] evals добавлены и проходят
[ ] зарегистрирован в skills.yml
```

### 5.2 doc-authoring (выжимка)

Обязательные разделы каждого дока по типу (из doc-profile); заголовочный блок диаграмм (scope, владелец, триггер обновления, last_verified); правило одного источника (ссылка, не копия); «генерировать > рисовать»; запрет доков вне профиля; стиль — короткие декларативные утверждения, без нарратива (доки читают агенты).

## §6. Команды и hooks

**Команды** (`.claude/commands/`, тонкие обёртки над протоколами):

| Команда | Что делает |
|---|---|
| `/aegis:init` | Фаза 1: Detect→Ask→Confirm→Materialize; флаги `--mode interactive|hybrid|autonomous`, `--preset <name>` (§7) |
| `/aegis:spec <тема>` | Интервью → spec.md (§8.1) |
| `/aegis:plan` | Brainstorm вариантов → architecture.md + ADR (§8.2–8.3) |
| `/aegis:tasks` | Декомпозиция в tasks.md (§8.5) |
| `/aegis:build <TASK-ID>` | Цикл задачи Фазы 3 (§9) |
| `/aegis:review <TASK-ID>` | Только линзы + отчёты (без реализации) |
| `/aegis:retro` | Мезо-контур самоуправления (§13) |
| `/aegis:audit` | Макро-контур: здоровье системы + gardener (§13) |
| `/aegis:status` | Сводка: вехи, задачи, красные проверки, бюджеты |

**Hooks** (`.claude/settings.json`) — детерминизм, ноль токенов:

```json
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command",
                    "command": "scripts/aegis/lint-changed.sh" }] }
    ],
    "PreToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command",
                    "command": "scripts/aegis/protect-paths.sh" }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command",
                    "command": "scripts/aegis/soft-checks.sh" }] }
    ]
  }
}
```

- `lint-changed.sh` — линт/typecheck только изменённых файлов (быстро).
- `protect-paths.sh` — блок записи в `constitution.md`, `standards/`, `skills/`, `registry/` для всех, кроме doc-manager (реестры) и человека; выводит причину блокировки агенту.
- `soft-checks.sh` — незавершённые TODO-маркеры, незарегистрированные роуты (предупреждение до гейта).
- Контракт hook'ов: PreToolUse с exit code 2 блокирует вызов, stderr возвращается агенту как причина — на этом построен `protect-paths`. `ConfigChange` дополнительно ловит попытки изменить настройки/hooks посреди сессии; `SubagentStop` — точка валидации handoff'а билдеров и линз.
- Полный гейт — `scripts/aegis/gate.sh` (Приложение B), запускается на PR/merge, не на каждый ход.

## §7. Фаза 1 — инициализация: Detect → Ask → Confirm → Materialize

Принцип: **интервью — это данные, а не промпт**. Вопросы, определяющие конфигурацию фреймворка, живут декларативными банками в `.aegis/interview/` (схема и стартовые паки — Приложение D), а конфигурация **детерминированно материализуется** из файла ответов `.aegis/answers.yml`. Исполнитель интервью тонкий — оркестратор в команде `/aegis:init`; вся предметность — в паках. Следствия: паки переносимы между проектами, версионируются, расширяются тем же draft-PR-циклом, что и протоколы (§5), и не занимают контекст оркестратора (слой 2, грузятся just-in-time).

### 7.1 Пайплайн

1. **Detect.** Explore-субагент (read-only) сканирует репозиторий: стек, build/test-команды, фактические конвенции, интеграции, greenfield/brownfield. Каждый факт предзаполняет ответ с confidence. Железное правило: **не спрашивать детектируемое**. Вопросы — только про намерения, которые из кода не читаются: цели, приоритеты NFR, компромиссы, аппетит к риску, командные практики.
2. **Ask** — по режиму (7.3). Пачки ≤3–4 вопросов (AskUserQuestion), трудное вперёд; у каждого вопроса видны default и `rationale`. «Не знаю» — легальный ответ: берётся default, пункт уходит в ledger. Вопросы `deferrable(phase2)` на init не задаются вообще — они прикрепляются к scope-интервью Фазы 2, где уже есть контекст фичи.
3. **Confirm.** Всё задетекченное подтверждается **пачкой одним экраном**, не по одному вопросу.
4. **Materialize.** Детерминированный генератор: `answers.yml` → поля CLAUDE.md (команды проекта), constitution, doc-profile, стандарты-заготовки, профиль S/M/L, набор линз, hooks. Конфигурация никогда не правится руками в обход answers — дрейф answers↔конфиг ловит `/aegis:audit` (§13). Изменение ответа → рематериализация → ревью диффа; это дёшево, потому что answers→config — чистая функция.

### 7.2 Банки вопросов и композиция

Пак проекта = композиция слоёв: `core` (режим, профиль, autonomy-limits, тестовый мандат, строгость линз, бюджеты) + `project-type/<T>` (с наследованием `extends:` — web-saas расширяет api-service) + `stack/*` (почти всё detect-only) + `context/*` (brownfield: подтверждение конвенций, frozen-зоны, delta-режим). Движок грузит только модули с совпавшим условием `when:` (например, `type == web-saas and not detected(auth)`).

Два инварианта, которые статически держит `bank-lint`: каждый вопрос обязан объявлять **`writes:`** — вопрос без конфигурационного следствия запрещён (goal-ориентированность, применённая к самой анкете), — и **`autonomy:`** — политику поведения без человека. Новый тип проекта = один YAML-файл, обычно через `extends:`; ни агенты, ни движок не меняются — это и есть механизм реюзабельности.

### 7.3 Режимы

- **interactive** — все blocking-вопросы по политике пака.
- **hybrid** (дефолт) — detect заполняет всё возможное; человеку остаются обычно 5–10 вопросов про намерения; остальное — batch-confirm.
- **autonomous** — ноль вопросов. Честность режима держат три механизма:
  1. *Полный путь разрешения:* у каждого вопроса есть detected-значение → declared default → эвристика пака; `bank-lint` проверяет это статически — пак с вопросом без пути разрешения в автономный режим не допускается.
  2. *Ledger допущений:* всё авторешённое пишется в answers.yml с `source: detected|default|heuristic`, confidence и однострочным rationale; значимые решения дублируются draft-ADR со статусом `assumed`. Первое касание человека — ревью ledger'а сверху вниз; любой ответ можно перевернуть, рематериализация перегенерирует конфиг.
  3. *`never-auto`-список* (миграции данных, публичные контракты, security-политика, платные сервисы, лицензии): такие вопросы берут консервативный default и встают в топ ledger'а; если безопасного default'а нет — init завершается со статусом `provisional`, а пункт становится blocking-гейтом перед Фазой 3. Автономный режим никогда не решает необратимое втихую и никогда не виснет молча.
- **Пресеты — главный множитель реюза:** `aegis init --mode autonomous --preset <name>` берёт answers-файл прошлого проекта как организационный дефолт; detect перекрывает только реально отличающееся. Организация накапливает свои дефолты как версионируемый артефакт (каталог пресетов), а init становится воспроизводимым в CI, а не сессией.

### 7.4 Специфика greenfield / brownfield

**Greenfield:** интервью намерений → генерация каркаса §1 → smoke-проверка: `gate.sh` зелёный на пустом проекте; каждый hook доказуемо срабатывает (провокация — запись в защищённый путь должна блокироваться).

**Brownfield:** detect глубже — фактические конвенции с confidence; `architecture.md` строится из кода с пометками `observed | inferred`; реестры заполняются задним числом (скан роутов/env/событий → черновики записей → batch-confirm пользователем); новые изменения идут delta-режимом через `changes/` (полная переспецификация legacy не требуется — истина нарастает инкрементально); frozen-зоны («это не трогаем») из context-пака попадают в constitution и в `protect-paths` hook; противоречивые конвенции — вопросом с вариантами, не догадкой.

### 7.5 Definition of Done инициализации

`answers.yml` без неразрешённых blocking-вопросов (или статус `provisional` с явным списком и гейтом перед Фазой 3); ledger отревьюен человеком либо явно отложен; CLAUDE.md в бюджете; constitution подписана человеком (в autonomous — после ревью ledger'а); реестры валидны по схемам; hooks доказуемо срабатывают; `/aegis:status` зелёный; профиль S/M/L зафиксирован (§15).

## §8. Фаза 2 — scope, brainstorming, архитектура, задачи

**8.1 Scope-элиситация** (`/aegis:spec`). Интервью о цели и границах; выход — `spec.md` (шаблон в Прил. A) с требованиями `R-*` в проверяемых формулировках. Для нетривиальных поведенческих требований — EARS-нотация («When <trigger>, the <system> shall <response>»): дёшево структурирует и убирает двусмысленность. Обязательный раздел «Вне scope» — главный инструмент против расползания.

**8.2 Brainstorm/оценка** (`/aegis:plan`, шаг 1). 2–3 архитектурных варианта, каждый — отдельным read-only research-субагентом в чистом контексте (легитимная параллель: пути независимы). Критерии сравнения берутся из NFR спеки, не изобретаются. Возврат — дистилляты ≤2k. Оркестратор синтезирует, выбор фиксируется ADR (включая отклонённые альтернативы — одна строка почему).

**8.3 Архитектура.** `architecture.md` по шаблону: компоненты и ответственность, контракты/интерфейсы (ссылки на схемы), диаграммы по doc-profile, NFR, ссылки на ADR. Контракты между модулями — обязательное условие будущей параллельности билдеров.

**8.4 Детализация фич.** На каждую фичу — `feature.md`: затрагиваемые модули, основной поток, **крайние случаи и негативные сценарии** (их потом гоняет lens-correctness — пишутся не для галочки), контракты входа/выхода, **end-to-end-проверка** (команда/сценарий, которым фича считается завершённой — способ самопроверки билдера).

**8.5 Задачи** (`/aegis:tasks`). Декомпозиция `feature.md` → `tasks.md`. Правила: размер задачи — «помещается в один контекст билдера» (метка S/M; L — дробить); явные `deps`; `R:` — какие требования закрывает; `AC:` — проверяемые критерии приёмки. 

**Гейт Фазы 2:** lens-consistency: каждое `R-*` покрыто задачами; каждая задача ссылается на `R-*`; противоречий spec↔architecture нет; недоспецифицированное — списком вопросов пользователю (аналог `/clarify`), а не молчаливыми допущениями.

## §9. Фаза 3 — цикл разработки

### 9.1 Цикл одной задачи (`/aegis:build TASK-ID`)

```
1 Контекст-пакет     оркестратор собирает по контракту делегирования
                     (feature.md, tasks#ID, фрагмент spec, стандарты) ≈3–6k
2 Реализация         Builder: план ≤10 строк → код + тесты вместе
3 Самопроверка       Builder гоняет тесты/сборку до зелёного (детерм.)
4 Линзы              параллельно, read-only, свежий контекст;
                     отчёты в reviews/, вердикты
5 Рефайнмент         оркестратор сводит blocking-находки → Builder чинит;
                     ≤3 итераций, дальше эскалация человеку
6 Доксинк            Doc-manager применяет handoff: реестры, диаграммы,
                     центральные доки (single writer)
7 Гейт               scripts/aegis/gate.sh — детерминированно (Прил. B)
8 Фиксация           commit по конвенции §12; NOTES.md обновлён;
                     tasks.md статус; новый контекст для следующей задачи
```

Набор линз шага 4 — по профилю (§15) и по типу задачи: correctness всегда; security — при новых роутах/вводе/зависимостях; architecture — при межмодульных изменениях; docs — при изменении контрактов; consistency — на закрытии фичи.

### 9.2 Правила параллельности (многопоточная разработка)

1. Параллель разрешена только между задачами с **непересекающимися write-scope** и объявленным контрактом в architecture.md. Порядок «контракт сначала»: интерфейс фиксируется до старта веток.
2. Каждая параллельная ветка — отдельный git worktree/бранч; у субагентов есть нативная `isolation: worktree`. Лимит по умолчанию — 3 билдера.
3. Центральные файлы (docs/, registry/, architecture.md) в ветках не трогаются — только заготовки в handoff; применяет doc-manager сериализованно при вливании.
4. Вложенные субагенты запрещены (уровень оркестрации, не только промпт).
5. Конфликт контрактов, обнаруженный билдером, — стоп ветки и эскалация оркестратору, не «локальный фикс».

### 9.3 Фидбек и дообработка

Blocking-находки линз (severity ≥3 или вердикт fail) обязательны к устранению; non-blocking Builder либо чинит, либо письменно отклоняет в handoff (одна строка почему) — отклонения видит человек в PR. Три неуспешные итерации — эскалация с сводкой «что пробовали». Паттерны повторяющихся находок уходят в `/aegis:retro` как кандидаты в протоколы (§13).

## §10. Тестовая система

**Юнит и интеграционные.** Конвенции — в `standards/testing.md` (раннер, структура каталогов, нейминг, что мокается а что нет); пишутся билдером вместе с кодом (никогда отдельным агентом-«тестером» — переспецификация контекста); негативные сценарии — из `feature.md#крайние-случаи`. Политика покрытия — «критичные пути и контракты», не проценты ради процентов.

**Property-based** — для инвариантов из `feature.md#контракты` (идемпотентность обработчиков вебхуков, сериализация туда-обратно, границы). Ловит то, что проходит выборочные юниты.

**Агентные (eval) тесты** — тесты самой агентной системы, `.aegis/evals/`:
- `skills/<slug>.yml` — срабатывание протоколов: {prompt, ожидание сработал/не сработал, ключевые действия}. Обязательны для каждого нового протокола (§5.1).
- `tasks/*.yml` — 10–20 реальных мини-задач проекта с проверяемым исходом (тесты зелёные, файл создан, реестр обновлён).
- Прогон headless (`claude -p ... --output-format json`) в CI; метрики: успех, число вызовов инструментов, токены, срабатывание нужных скиллов.
- **Правило:** изменения `.claude/` и `.aegis/standards|skills` мержатся только при эвалах не хуже baseline. Это страховка масштабирования: рост системы не ломает срабатывание старого.

## §11. Документация и диаграммы

**Doc-profile** (`product/doc-profile.yml`, выбирается на init):

| Профиль | Обязательные артефакты |
|---|---|
| web/SaaS | C4 context+container, ERD, API-док (генер. из OpenAPI), sequence критичных флоу |
| data/ETL | dataflow, lineage, schema-реестр, контрактные тесты источников |
| library/SDK | генерируемый API-reference, примеры использования; без C4-контейнеров |
| stateful/embedded | state machines, timing-заметки |

lens-docs и doc-lint проверяют **только профиль**. Вне профиля — не создавать (принцип «не засорять» как исполняемое правило, а не пожелание).

**Диаграммы-как-код.** Формат по умолчанию Mermaid (`flowchart`, `erDiagram`, `sequenceDiagram`, `stateDiagram`) — диффуемо, дёшево, рендерится в GitHub/CI. Для строгого C4 — Structurizr DSL (одна модель → согласованные вьюхи), честной ценой +1 инструмент. У каждой диаграммы заголовочный блок: scope, владелец-артефакт, триггер обновления, last_verified.

**Антидрейф:** `registry/diagrams.yml` держит `watches:` (глобы кода); hook при структурных изменениях помечает диаграмму stale; stale на гейте закрытия фичи — blocking. **Генерировать > рисовать:** ERD из миграций, API из OpenAPI, зависимости из кода; рукой — только rationale, который нельзя сгенерировать.

**Организация.** `docs/` мал и стабилен (architecture overview, integrations по одному на систему, runbooks по профилю; `index.md` генерируется). Детали фич живут в `.aegis/specs/<feature>/` и в docs/ не дублируются (ссылка, не копия). Агенты входят в документацию через реестры-индексы, а не грепом дерева — размер docs/ не стоит токенов.

## §12. Целевая цепочка и трассируемость

```
mission → roadmap(веха: измеримый исход) → SPEC-042(R-1..R-n)
        → FEAT → TASK-042-03(R:, AC:) → commit/PR → lens-reports → merge
```

Конвенции: commit `feat(TASK-042-03): ...`; PR-шаблон с полями Spec / Tasks / Lens-verdicts / Registry-changes. `trace-check` на гейте: у изменённых модулей есть TASK-ID; статусы tasks.md консистентны с ветками; каждое R-* закрытой фичи покрыто зелёной задачей; «сиротский» код (без TASK-ID) — fail. Goal-ориентированность здесь — не лозунг, а проверяемое свойство: от любой строки кода восходимая цепочка до вехи roadmap.

## §13. Самоуправление и метрики

Три контура:

| Контур | Ритм | Механика | Выход |
|---|---|---|---|
| Микро | каждая задача | самопроверка → линзы → рефайнмент ≤3 → гейт | merge / эскалация |
| Мезо | веха / неделя | `/aegis:retro`: анализ lens-отчётов, падений гейта, токен-метрик; поиск повторов | draft-PR протоколов/стандартов |
| Макро | по расписанию | `/aegis:audit`: реестр-линт, докдрейф, дрейф answers↔конфигурация, бюджеты, gardener; дешёвый Haiku-проход по реестрам на семантический дрейф | health-отчёт + draft-PR |

**Метрики** (пишутся hook'ами в `.aegis/memory/metrics.jsonl`, агрегирует audit): токены/задачу по типам; доля падений гейта по причинам; acceptance rate находок линз (<~30% — линза шумит, чинить её протокол или выключать); инциденты докдрейфа; срабатывания скиллов (для gardener).

**Границы самоуправления (жёстко):** агенты предлагают (draft-PR с маленьким диффом), человек апрувит; `constitution.md` — только руками человека; `protect-paths` hook делает это физически, а не декларативно. Автономная само-эволюция правил — задокументированный анти-паттерн фреймворка (см. §17).

## §15. Профили адаптации

| | S (solo / ≤2 недель) | M (команда / месяцы) | L (много потоков) |
|---|---|---|---|
| Агенты | один (без субагентов) | оркестратор + 1–3 билдера | полный ростер §4 |

| Реестры | integrations (если есть) | + skills, diagrams, env | все §3 |

| Самоуправление | — | retro на вехах | retro + audit по расписанию |

Профиль выбирается на init и **может расти** (S→M→L) командой `/aegis:audit --upgrade-check`, когда метрики бьют пороги §16. Обратное тоже верно: если L-механика не окупается — вернуться на M. Фреймворк, который нельзя ужать, сам становится bloat'ом.

## §16. План внедрения и пороговые правила

**Этап 0 (день 1–2):** профиль S. Один агент, артефакты, hooks, гейт. 
**Этап 1 (неделя 1):** первая линза (correctness) в свежем контексте. Критерий успеха: находит реальные дефекты; ложные <~30%.
**Этап 2 (недели 2–3):** параллель по чистым контрактам, лимит 3. Критерий: суммарные токены/задачу ≤ ~3–4× при измеримом выигрыше; иначе откат.
**Этап 3 (месяц 2):** эвал-харнесс + доксинк в CI; baseline-правило для изменений `.claude/` и стандартов.

**Пороговые правила (меняют решения, а не украшают):**
- Контекст регулярно >70–80% лимита при падении качества → сначала компакция/декомпозиция задач, потом субагенты.
- Инструментов у агента >15–20 → selective loading / tool search, а не новая роль.
- Тесно связанный код с общим состоянием → один агент (кодинг параллелится хуже research — прямое наблюдение Anthropic).
- Ценность задачи низкая → без мультиагента: кратный токен-овербюджет не окупится.
- Линза с acceptance <30% два ретро подряд → чинить протокол или отключать.
- Один и тот же фидбек ≥2–3 раз → кандидат в протокол (петля расширения).

## §17. Ограничения и честные оговорки

1. **Перенос цифр.** 90.2% прироста и «токены объясняют 80% дисперсии» — внутренние эвалы Anthropic в research-домене; на кодинг напрямую не переносятся, Anthropic сам отмечает худшую параллелизуемость кодинга.
2. **LLM-as-judge.** Линзы наследуют position/verbosity/self-enhancement bias, preference-leakage и нестабильность между прогонами (Zheng et al. 2023 и последующие). Поэтому линзы совещательны, решают детерминированные ворота; не использовать одну модель как единственного автора и единственного судью критичных решений.
3. **Автономная само-эволюция правил** — недоказанная практика; в Aegis она запрещена архитектурно (draft-PR + protect-paths), а не пожеланием.
4. **Порог деградации селекции скиллов** количественно неизвестен; митигируется нэймспейсами, анти-триггерами, слиянием и gardener-аудитом, но это управление риском, не гарантия.
5. **Upfront-стоимость.** Реестры, эвалы и профили окупаются на мультиагентных проектах длиной в месяцы; для мелких проектов честный ответ — профиль S, а не «весь фреймворк».
6. **Экосистемный дрейф.** Имена hook-событий, поля frontmatter и поведение раннера меняются между версиями Claude Code. Использованные здесь API сверены с документацией на июль 2026 (события PreToolUse/PostToolUse/Stop/ConfigChange/SubagentStop; поля `skills`, `disallowedTools`, `maxTurns`, `memory`, `isolation: worktree`; плагины как юнит дистрибуции) — перед внедрением сверяйте повторно. Фреймворк ставит на паттерны (слои контекста, реестры, детерминированные ворота), а не на конкретные API.

## §18. Надёжность, безопасность контура и дистрибуция

### 18.1 Отказоустойчивость и восстановление

- Истина в артефактах (§0.П1) ⇒ каждый шаг ре-раннабелен: упавший билдер перезапускается с чистым контекстом от `tasks.md` + handoff-заготовок; `gate.sh` идемпотентен — повторный прогон безопасен.
- `NOTES.md` — контрольная точка оркестратора; обновление после каждой вехи и есть чекпойнт. SessionStart-hook (source: resume|compact) переинжектирует указатель на NOTES.md и текущий TASK-ID.
- Компакция по правилам: PreCompact-политика сохраняет принятые решения, список изменённых файлов, команды тестов и открытые вопросы; остальное сжимается.
- Ретраи: транзиентные падения инструментов — повтор ≤2; систематические — эскалация, не цикл; `maxTurns` в frontmatter — предохранитель последней линии.

### 18.2 Безопасность агентного контура

lens-security проверяет продуктовый код; этот раздел — про сам контур:

- **Prompt injection:** любой внешний контент (payload вебхука, сторонний код, выдача web-инструментов, текст тикетов) — данные, не инструкции. Правило зашивается в системные промпты ролей; агент, обрабатывающий внешний контент, работает с минимальным набором инструментов; подозрительные конструкции ловит PreToolUse-фильтр.
- **Least privilege:** tools-allowlist по ролям (§4) + `disallowedTools`; линзы физически без Edit/Write; Bash — только по маскам; `bypassPermissions` запрещён constitution.
- **Секреты:** только env-ссылки (§3); PreToolUse-hook блокирует чтение `.env`-файлов и запись строк, похожих на секреты; секреты не попадают в handoff и отчёты линз.
- **MCP-серверы:** только из реестра `mcp.yml`; добавление — через draft-PR; инструментам стороннего MCP — минимальные scope.

### 18.3 Дистрибуция Aegis и версионирование

- **Упаковка — плагин Claude Code:** `agents/`, `skills/`, `commands/`, hooks и MCP-конфиг едут одним версионируемым юнитом (`.claude-plugin/plugin.json`) и распространяются через marketplace организации; локальная проверка — `claude --plugin-dir`; организационный раскат — управляемые настройки (extraKnownMarketplaces / enabledPlugins).
- **Важная особенность:** CLAUDE.md в корне плагина НЕ загружается как контекст проекта — проектное состояние (CLAUDE.md, `.aegis/`) материализует `/aegis:init` (§7). Это совпадает с дизайном: **плагин = поведение, init = состояние проекта**.
- **Версионирование:** semver плагина; обновление → рематериализация answers→config (§7.1) + прогон eval-харнесса против baseline (§10); несовместимые изменения схем реестров — миграционный скрипт в составе релиза.

## Приложение D. Интервью-система: схема вопроса и стартовые паки

**D.1 Схема вопроса**

```yaml
- id: q.<layer>.<slug>           # уникален по всем банкам
  phase: init                    # init | phase2 | on-trigger:<expr>
  when: "type == web-saas"       # условие включения: тип, ответы, detected()
  ask: "<текст вопроса>"
  kind: single                   # single | multi | scale | free | confirm
  options: [...]
  default: <значение>            # обязателен при autonomy != always-ask
  writes: <артефакт>#<поле>      # ОБЯЗАТЕЛЕН: вопрос без следствия запрещён
  autonomy: always-ask           # always-ask | auto-if-detected(conf>=0.8)
                                 # | auto-default | detect-only
  severity: blocking             # blocking | deferrable(phase2) | optional
  rationale: "<зачем спрашиваем — показывается пользователю>"
```

`bank-lint` проверяет статически: уникальность id; наличие `writes` и `autonomy` у каждого вопроса; путь разрешения (default или детект) при autonomy ≠ always-ask; корректность `when`-выражений; допуск пака к автономному режиму.

**D.2 core.yml (стартовый, сокращённо)**

```yaml
- {id: q.core.mode, ask: "Режим init?", kind: single,
   options: [interactive, hybrid, autonomous], default: hybrid,
   writes: answers#mode, autonomy: auto-default, severity: blocking,
   rationale: "Определяет весь ход интервью; переопределяется флагом CLI"}
```
