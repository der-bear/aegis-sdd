# Retro 0003 — TASK-STABLE-01, abandoned at the cap

2026-09-18, **corrected 2026-09-19** after an independent review read this file and the tree. Two of
its claims were false and are struck below rather than edited out: that the framework escalated (I
did), and that forty files belong to no task (nineteen do). The fourth cycle of this dogfood.

## What the cycle did

Sixteen requirements under one lease. Seven converged and their findings are closed: size budgets
warn at every stage (R-1), `aegis next` escalates at the round cap instead of advising a round the
gate will refuse (R-2), the Claude Code commit hook and its shell parser are deleted so one barrier
stands in the commit path (R-3), delegation is data read from `HEAD:.aegis/answers.json` (R-5),
`aegis diff` and `diff_digest` ask one function (R-7), the documents say what the code does (R-8),
and the tree is not edited between dispatching a round and the last lens reporting (R-16).

Two did not converge: R-4 and R-6, the attribution half. They are why the task was abandoned.

**Counted.** 255 tests, `make lint` clean, the bootstrap gate green. Three lens rounds; across the
four tasks of this dogfood: correctness 45 findings at 0.73 acceptance, design 70 at 0.74, security
41 at 0.63, and zero reopened findings in the whole dogfood. Packet mean 2,137 tokens, max 3,165.
Gates: 3 passed, 12 failed, the failures dominated by `reviews` (11) and `trace` (6) — which is the
shape of this retro in one line.

## Why it was abandoned

**Because design was at 3 of 3 rounds with an open severity-3 finding.** Any edit to close it forced
a fourth round for design, which the cap forbids, so the task could not reach green. That is the
whole reason, and it is narrower than what this file said first.

~~*"The class blocked every round of three consecutive tasks, so rule 5 fires."*~~ Struck. The
attribution mechanism has grown three times in three tasks, which is the real cost and is why ADR-5
caps it at five records — but the rule added this cycle was **one** repair old, not a class surviving
two, and the framework's own trigger for rule 5, a finding marked fixed that came back, has fired
zero times in four tasks. Calling it rule 5 dressed a correct decision in a mechanism that had not
fired.

**And the framework did not escalate — I did.** Reproduced: at `rounds == cap` with an unmoved digest
and an open severity-3 finding, `next_action` returns `fix <finding> in the code [agent]`. The
escalation branch sits inside `if record.diff_digest != plan.diff_digest`, and the second one tests
`rounds > cap`, strictly greater. `lens_record` then accepts round cap + 1 without complaint; only
`check_reviews` says the limit is exceeded. So the loop would have sent me to fix, re-dispatch and
burn a fourth round. R-2 is half implemented, which is item 2 below and a requirement for the next
task.

**What does hold, and is why ADR-5 deletes the rule rather than tuning it: in round 3 one rule
failed in both directions at the same time.** The base-agreement check added
this cycle refuses legitimate work on a brownfield branch that diverged from the mainline before
Aegis was adopted — correctness reasoned it through and noted the check is inert on *this* branch,
so it reported the refusal honestly as derived from the code rather than observed. And security
found its trust root is `default_base`, which falls through to the local `main` ref: one
`git branch -f main <payload-commit>`, which no installed hook sees, makes the base agree with
itself. Over-restricting and under-protecting at once is the signature of measuring the wrong
thing. A patch adjusts a threshold; this needed a different question.

**The finding I read as unpatchable is the trust model, and it was never the cheapest route.**
Security's F-66b7d183 is true: write `"status": "merged"` plus a four-key merge receipt and the merge
gate passes on unreviewed code. But `lens_record` validates the schema, the lens name and the digest
and nothing about the content, so `{"verdict": "pass", "findings": []}` per required lens has always
produced the same green gate with no file forged at all — and ARCHITECTURE said before this cycle
that approval rests on git history and code review, not on signatures. Security's own round-1
F-414d9b0b called the receipt "no harder than forging a gate receipt was before" and filed it as *not
a finding*; round 2 rated the same fact severity 4 because a code comment had become false. The
comment is false and goes. The exposure did not change, and I spent an hour treating a documented
model as a regression I had introduced.

## What to do differently

1. **A verification pass belongs to every document the change touches, scheduled before the last
   round the cap allows.** It is in R-16 now. It found 22 false claims in documents I had written
   hours earlier, and mechanical checks — `check commands`, `check protocols`, `check pointers` —
   were green through all of them.
2. **R-16's prose half should be on the script side.** Design is right: `lens plan` could record the
   digest it dispatched, and `lens record` could store a report bound to it marked stale instead of
   discarding it. That would have *recovered* this task's two lost reports rather than asking each
   round to be careful. A requirement for the converging task.
3. **A lens's reconciliation is worth more than its findings.** Correctness closed all nine of its
   priors with evidence, design seven of eight, security seven of eight. The work of the previous
   round converged; only the new mechanism did not. Without carried dispositions I could not have
   known that, and would have read three failing verdicts as three failures.
4. **Do not re-issue a task before the fork is answered.** Any re-issue covers the same files —
   `checks.py`, `flow.py`, `core.py`, `tests/**` carry both halves, and a lease cannot split a file —
   so its fresh security lens meets F-66b7d183 in round 1. The absence of a TASK-STABLE-04 is
   deliberate, and this sentence is here so nobody wonders.
5. **`aegis next` advises past an open owner decision, and cannot express one.** With
   TASK-STABLE-01 abandoned it says "build TASK-STABLE-02" — work ADR-5 forbids until the fork is
   answered, because any task over these files meets F-66b7d183 in its first round. R-2 taught `next`
   to escalate at the round cap; it has no state for "blocked on a decision recorded in an ADR". The
   loop is computed from disk, so the fix is on the script side: an ADR whose status is `proposed`
   and which names a blocking question should make `next` say *that* instead of the next task. Found
   here, one minute after the abandonment, by running the command.
6. **The framework cannot commit its own escalation, and that is the sharpest process finding of
   the cycle.** Observed after the abandonment: a commit carrying retro 0003, ADR-5 and NOTES.md was
   refused by the installed hook — 19 `trace` failures, because the code TASK-STABLE-01 reviewed now
   belongs to no task, and `requirements: not covered by any task`, because R-1..R-8 and R-16 lost
   their only citing task. The designed way out of an abandonment is to re-issue, and ADR-5 defers
   re-issuing, so the two documents that record the stop stay in the working tree. The round's
   evidence did commit (`e8bbace`): the hook exempts a commit wholly inside `.aegis/runs/`. The
   exemption should cover `.aegis/memory/**` and `.aegis/decisions/**` too — neither is ever code,
   and the moment a retro is written is the moment `trace` is most likely red. Not fixed here:
   `scaffold.py` carries the hook template and no round remains to re-review it.
7. **The framework escalated to a person, which is its design.** The standing instruction to carry
   the framework to optimality autonomously was given before this evidence existed, and it does not
   override the framework's own rule. Choosing (c) — the v2 rewrite — at the end of a session, on my
   own, would be the reset counter with a legal-looking face.

## Found by the independent review, after three lens rounds had passed the same tree

1. **The build protocol is exempt from ownership, and R-16 edits it.** `capabilities.json` lists
   `**/build/**` under `generated_paths`, and `check_trace` excludes those matches — so
   `skills/build/SKILL.md`, the file R-16 changes, was in the digest and in the diff every round and
   never under `trace`. Verified: `matches_any("skills/build/SKILL.md", ["**/build/**"])` is True.
   Its vendored copy is `.aegis/**` and skipped for a different reason. At the merge scope 21
   non-`.aegis/` files are in scope and 19 are orphans; the missing one is exactly this file. Every
   adopter with a `build/` or `dist/` source directory inherits it.
2. **`next` at the cap advises the dead end.** With `rounds == cap`, an unmoved digest and an open
   severity-3 finding it says `fix … [agent]`, whose note is to re-record the lens; `lens_record`
   accepts round cap + 1 silently and only `check_reviews` objects. `NextEscalatesAtTheCap` locks the
   digest-moved branch alone, so the test I wrote for R-2 passes on the half that was built.
3. **`_land_pending` and `land` count a receipt the default branch already contains.** Both test
   ancestry of HEAD and never of the default branch's tip, so after one landing plus one bookkeeping
   commit `_land_pending` is true for ever: `next` puts a human step at the top after every commit
   and `next --run` stops there. One condition fixes it.
4. **A severity-2 finding in my own map is a false positive, and my fix for it adds a sixth guard.**
   Security's `may_waive`-has-no-floor finding assumed `aegis waive verify` would succeed. It cannot:
   `WAIVER_SCHEMA`'s `check` enum holds no `verify`, `trace`, `drift`, `reviews` or `handoff`, and
   `waive` validates the candidate before writing. `findings_to_steps` proposed a refusal list for a
   hole the schema already closes — the growth ADR-5 exists to stop, inside ADR-5's own handoff.
   Withdrawn there.
5. **The count.** ~~"Forty files belong to no task"~~ — it is 19. Forty was
   `git status --porcelain | wc -l`, every uncommitted file rather than every orphan, written into
   this file, NOTES and the handoff. In the retro whose own second lesson is that a number counts
   only once it has been measured.
6. **The packet said tier C and the gate judged tier A, and my own prose is what raised it.**
   `AUTH_HINTS` matches `\bauthoriz` anywhere in the diff text, and this diff's diff text includes
   ARCHITECTURE's new "Authority is data" section — the word *authorise* in a paragraph about
   delegation. So `auth` was detected, `_risk_tier` returned A at `lens_plan` and `check_reviews`
   while the manifest kept the C it was created with, and the gate did say "risk tier A requires 2
   review rounds". Inert here — every lens ran at least twice and no reviewer name matched the
   builder — but a documentation sentence about authorisation should not raise a change's risk tier,
   and the tier a task is briefed with should not differ from the tier it is judged by.
7. **The R-7 receipt carve-out in the git hook is a no-op against forgery.** Forcing the gate to run
   on a commit carrying a receipt does not help when the gate reads the forged receipt and passes;
   `merge_receipt_files` already ignores a receipt whose `sha` is not behind HEAD.
   `TheReceiptIsNotExempt` locks behaviour that changes nothing.
8. `merge_receipt_files` never checks `receipt["task"] == task_id`, unlike `gate_receipt_valid`.
   Copying one task's receipt into another's directory yields "claimed by several" — fail-closed.
9. `.aegis/changes/universal-01/tests_hook_simplify.py` still references `core.commit_scope` and
   `hooks/pre-commit-gate.sh`, both deleted by R-3, which said to delete its tests too.

Seven of these nine are in files three lens rounds read. The two that are not — the `build/**`
exemption and the tier mismatch — are in generated configuration and in a computed plan, which no
lens is briefed to reconcile against the manifest. That is the gap worth naming: **the lenses review
the diff, and nothing reviews the configuration the diff is judged against.**

## What happened next, 2026-09-19

The owner asked whether the whole thing was over-built — "не слишком ли жёсткие guardrails
для агентной разработки и современных моделей". The honest answer was yes, with receipts: three
of four tasks abandoned at the cap, the framework unable to commit its own retro, an opinion
that a wrong number in a table forced a task's abandonment, ~1.5M review tokens per task, ten
places where the loop stopped for a person who had said «реши сам», and a focus/unfocus dance
for every note. The pattern: every time a lens found a way around a guard, a guard was added,
until the guards were the main thing the framework did.

The owner's instruction was then to finish, simply, without ceremony. Four commits did it, and
the deletion commit alone is −2,981/+215. This retro's own findings 1–9 are closed by them
except R-9/R-10 and R-11..R-15, which stay planned and small. The lesson that outranks the rest
of this file: **a check observes and reports; a refusal blocks the agent mid-work. Keep the
checks. Delete the refusals. One refusal point — the merge boundary — is enough.**
