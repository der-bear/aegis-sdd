# Retro 0002 — TASK-UNBLOCK-03, and the tension the round cap exposed

Date: 2026-09-18. Cycle: the third task of the aegis-on-aegis dogfood.
Retro 0001 covers TASK-UNBLOCK-01 and -02; this one covers -03 and is where the next task's
requirements are written down.

## What the cycle did

ADR-4 rebuilt adoption attribution on **content** rather than history, which made the adoption
commit the documentation instructs possible for the first time. Alongside it: a `finding` waiver
kind; the rule that a blocking finding is dismissed only by a person who is neither the builder
nor the lens, in one implementation read by both the gate and `aegis next`; an exact-match
commit-hook exemption with tested detection; evidence that tests actually ran, read from runner
output; `aegis check commands`, so a documented command that cannot run is a gate finding; an
AGENTS.md chain byte budget; four handoff fields; and `aegis git-hooks install` plus CI — the
barrier outside Claude Code that the sources audit named as the highest-value missing piece,
ahead of the graph.

Three rounds, three lenses, 43 findings. All three lenses ended with zero blocking open, as they
also did in TASK-UNBLOCK-02 — the difference this time is that **the task gate is green**, which
neither earlier task reached. 213 tests pass; the receipt is bound to digest `7942d66a9fd82cf9`.

The deepest finding was structural and came from two lenses independently: git stores a symlink
as a blob holding its target, while the baseline recorded a link as `symlink:<target>`, so a
64-hex digest could never equal the record. A baselined symlink was therefore **never** in the
adoption state at HEAD — it stayed in the scope of every task and the baseline could not retire
by being committed, which is the single thing ADR-4 exists to enable. One function, `_git_key`,
now keys both sides. The security lens then probed the obvious forgeries — a regular file whose
bytes are literally `symlink:real.py`, a hand-forged 100644 index entry, a staged repoint — and
all three stay in scope while the committed link is exempt.

## The tension worth remembering

**A green task gate does not imply a committable state.** Document freshness and review freshness
are two independent checks bound to the same files, and once the round budget is spent they can
only be satisfied one at a time: correcting a document moves the digest and invalidates the
reviews, while leaving it uncorrected blocks the merge. This cycle ended in exactly that vice,
and so did the previous one — TASK-UNBLOCK-02 ended red because fixing the design lens's last
advisories about EVALUATION §8 moved the digest with no round left.

Twice is a class, and rule 5 says a class that survives its fix means the mechanism is wrong.
The mechanism here is **review bound to a moving working tree**. ADR-1 is the answer already on
record: when review and gate are attestations over a candidate commit, the diff stops moving and
the two freshness checks stop competing. This cycle is the second empirical argument for it.

**The cheap process fix, available now:** run the document verification pass *before* the last
lens round, not after. Belongs in `skills/build/SKILL.md` step 5 as a sequence change.

Second lesson: **mechanical checks passing is not the documents being true.** `check commands`,
`check protocols` and `check pointers` were all green while three prose claims in ARCHITECTURE
were false against the code. A command existing is not a sentence being true.

## Why `architecture` was left unattested

A read-only verification pass over `docs/ARCHITECTURE.md` against `scripts/aegis/aegis_cli/**`,
`hooks/**` and `workflows/**` found three claims false against the code. Signing it would put a
name on claims there is written evidence against, which is worse than an unowned stale marker.

1. **:134** — "`check pointers` (bootstrap and task gates) fails when the import line is gone."
   The bootstrap gate (`flow.py:1506-1514`) runs structure, protocols, commands, banks, drift,
   budget, registry — not `check_pointers`, and `check all` skips it too. A `CLAUDE.md`
   overwritten right after `init` passes `aegis gate --stage bootstrap`. Both a false sentence
   and a real gap: the pointer file is how every rule reaches the agent.
2. **:282-283, and README:260** — `aegis diff <TASK>` covers "exactly the files the digest
   covers". `diff_digest` includes `.aegis/answers.json` (`core.py:552-557`); `task_diff` drops
   it (`flow.py:527-529`). `check_trace` itself says the digest covers `answers.json` so that
   changing it invalidates every review — yet the reviewer bound to that digest is never shown
   the change. A review-integrity hole, not a wording slip.
3. **:309-313** — the hooks "run the same merge gate for every commit in the checkout" and each
   "refuses when that path is gone". `scaffold.py:254,287` fall back to `command -v aegis` and
   refuse only when both are empty, so a *different* `aegis` on PATH runs the gate.
   `scaffold.py:263-267` exempts any commit whose staged set lies entirely under `.aegis/runs/`
   — a **prefix** exemption, broader than the exact match §6 calls "nothing to get around", and
   it therefore also exempts a commit containing nothing but `gate-receipt.json`. Pre-commit runs
   `--no-run` while pre-push runs commands, so "the same" is loose. **This is the one to fix
   first:** the receipt is the gate's own evidence, and it sits inside the exempt prefix.

`cli-reference` and `usage` were verified to hold no false claims within their watched sources —
every command, flag and check name cross-checked against `build_parser()`, and the roles table,
slash commands, workflow name and codex-lens invocation checked line by line — and were attested
by the session agent, with the signature naming the agent rather than a person.

Two claims sit **outside every watched glob**, so no digest will ever catch them (README:207-244):
"a runner nobody recognises produces 'the gate cannot tell', not a pass" — it warns and the gate
passes; and "A status that cannot be asserted" — the receipt is unsigned JSON that no hook
protects. ARCHITECTURE:298-299 words the same idea correctly. Registering that section under a
watching document is its own small requirement.

## Requirements for the next task (found after the round budget was spent)

Three touch the same two functions and should land as one change with its own tests:

1. **A regression this task introduced, in the mechanism meant to stop false greens** (sev2).
   `go test -run NoSuch ./...` exits 0 and prints `ok <pkg> 0.004s [no tests to run]`, which the
   round-2 go pattern matches, so `tests_ran` returns `ran` and a filter that matched nothing is
   accepted — the case its own docstring names. Before round 2 that output was `unknown` and drew
   a warning; now it is a silent green. Latent rather than live here: this project's only test
   command is `make test`. Fix: `(?! \[no tests to run\])` in the go pattern, narrow the bare
   `PASS` alternative to `^--- PASS:`, and add `no tests to run` to `_TESTS_NONE`.
2. **`git ls-files -s -- <rel>` takes a pathspec, not a literal** (sev1). A baselined name
   containing `?`, `*` or `[` lists every match and `split()` keys the first: probed `x?.md`
   beside `x1.md`, and `_digest_in_index` returned `x1.md`'s blob. `ls-tree` is literal, so
   `_digest_at` is unaffected. Fix: query `":(literal)" + rel`.
3. **The two sides of the symlink key decode differently** (sev1). `content_key` uses
   `os.readlink` (filesystem encoding); `_git_key` decodes the blob as UTF-8. Off a UTF-8 locale
   a non-ASCII target keys differently on the two sides and never reaches the adoption state.
   Fix: `"symlink:" + os.fsdecode(blob)`.

And separately:

4. **`aegis status` overstates the baseline.** It reports every recorded uncommitted path as
   "attributed to adoption": measured, `_pre_adoption_files` returns 13 and `status` says 15,
   because `CLAUDE.md` and `AGENTS.md` were baselined and then rewritten, so they belong to a
   task. `flow.py:1893-1901` computes `pending` from `changed_files | working_tree_files`. Fix:
   count what the attribution function returns and report the rest as a separate line. Same class
   as the whole task — a tool claiming more than it checked.
5. **The exec bit is not part of the adoption key.** `content_key` and `_git_key` drop the mode of
   a regular file, so `chmod +x` on a baselined path is invisible in the tree, the index and at
   HEAD — probed. `diff_digest` already argues that an exec bit changes what runs without changing
   a byte, so the two mechanisms disagree. R-27 attributes by content and is silent on mode, so
   this is a design question: key an executable as `exec:<sha256>`, still accepting a bare hash
   for baselines already recorded.
6. **The three ARCHITECTURE corrections above**, plus EVALUATION §8's `Rounds | 2 → 3 (the cap)`
   and how this third cycle ended, plus the README omissions the verifier listed (`compile`,
   `scaffold`, `lease check|show`, `check all`, `--root`, `gate --task/--no-run`,
   `check --task/--base/--feature`).
7. **The CI workflow states one claim twice** — two consecutive header paragraphs both end "which
   is the only place the invariant actually holds". Repetition is how a rule stops being enforced.
8. **On `push: [main]` the merge gate's diff scope is empty**, because `_default_base` resolves
   `origin/main`, which is HEAD there. The non-diff-scoped half still runs. Either diff against
   the push event's before-sha, or say in the workflow which half each job runs.
9. **Carried from retro 0001, still open:** `aegis next` advises a lens round that would exceed
   the cap instead of escalating (it behaved correctly this cycle only because the reviews were
   fresh); a waiver of any kind other than `finding` mutes a check with no person as owner, and
   both live waivers are agent-owned; `aegis lens disposition` accepts a one-character `--by`.

10. **After the merge gate marks a task `merged`, the branch cannot take another commit until it
    lands.** Found by the installed pre-commit hook itself, on the very next commit: the merge
    gate's `trace` diffs against `_default_base` (the merge-base with `main`), the task's 48
    files are in that scope, and a `merged` task no longer owns them — "changed file belongs to
    no task", 48 times. The block is a defensible invariant (a gated candidate should not drift
    before it lands); everything around it is wrong: the message names a different problem, the
    only remedy is landing, which the framework neither performs nor names, and `merged` is a
    written status that git contradicts until someone moves `main`. This is the third empirical
    receipt for ADR-1: status derived from the commit graph, and **land** as an explicit step.
    Until then, `aegis next` after a green merge gate should say "land the branch" with the
    command, and the run-directory bookkeeping commit should stay exempt, as it is.
